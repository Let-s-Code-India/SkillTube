AI assistants can use more than a model alone. A reusable instruction set, a small tool, a dataset or a workflow can make a repeated task easier to explain and reproduce. Yet these resources are spread across public repositories, each with its own naming and documentation habits. Someone who knows exactly what they need may find it. A newcomer often has to guess where to begin.

We built SkillTube to make that first discovery step less dependent on guessing repository names. A listing has a short name, a concise description, a longer explanation and structured tags. Those details let a visitor scan several options before opening a repository. The goal is not to replace project documentation; it is to offer a consistent first view and a reliable path to the source.

AI skills are the main focus, but the same discovery problem applies to MCP servers, datasets, databases, prompts, agents and AI tools. These projects have different installation steps and requirements, but people still need to know what each one does, who maintains it and where its code lives. A shared directory can make those differences easier to compare without pretending the resources are identical.

SkillTube keeps listings connected to their public GitHub repositories. Developers keep their code, history, issue tracker and licence in place. The directory adds cards, tags, developer channels and public pages. It does not host the resource files, and it cannot guarantee that a third-party project is safe or suitable. Visitors should still read the repository and check its licence before using anything.

We also wanted the project rules to be inspectable. SkillTube is open source, uses documented backend functions, and publishes community, privacy and reporting policies. GitHub ownership checks and the catalog job are meant to support accurate listings, while reports give developers an opportunity to respond. These safeguards reduce uncertainty, but they are not a substitute for reviewing code or data.

The project is intentionally plain: browser modules without a framework build step, public pages that can be read without JavaScript, and no advertising or analytics. This keeps the product understandable to contributors and accessible to visitors on modest devices. It also makes the limits visible: public discovery depends on the information developers provide and on the services that host the site.
